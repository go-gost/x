# Plan: Move the tun-to-tun link out of p2p into GOST, over a p2p datagram tunnel

**Date:** 2026-09-11
**Status:** Implemented (see Implementation notes at the end)
**Scope:** `plugin/p2p` (protocol), `x/` (p2p wrapper + tun handler), `p2p/` (tunnel host)

## Context

The tun→tun link currently lives entirely inside the `p2p` host: `--link "p2p0=<key>"`
opens a device that must already exist (`p2p/dev.go`, `p2p/link.go`) and bridges raw
chunks over one persistent smux stream. p2p therefore owns device attach, framing and
the link role, while device creation, addressing, MTU, routes and DNS are the caller's
problem — and a tun is exclusive-open, so it can never be shared with GOST's own tun
listener.

GOST already has a complete, documented tun stack: the `tun` listener creates *and*
configures the device (`net`, `mtu`, `name`, `dns`, `route`, `routes`, `gw`), and the
`tun` handler in client mode bridges that device to a datagram connection obtained from
the service's chain. The goal is therefore: **GOST owns the device, p2p is only the
pipe**, reproducing the existing `--link` capability by configuration instead of by p2p
code.

Two questions were raised:

**1. How does p2p replace the `router` handler?** `x/handler/router/` does two jobs:
(a) it is the *transport hub* — clients dial it with the relay associate protocol, it
frames IP packets (`packetConn`, 2-byte length prefix) and reaches other nodes over its
UDP `entrypoint` mesh; (b) it holds the *routing table* (dst IP → gateway →
connector, fed by `routers:`/ingress) and dispatches to the peer owning the destination.

With p2p, (a) disappears: every peer pair gets its own direct datagram channel, with
relay fallback and NAT traversal handled by p2p — no hub node, no associate framing, no
`entrypoint` UDP mesh. (b) moves to each node: the device's own addressing plus the tun
listener's `route`/`routes`/`gw` metadata (a single link is point-to-point, so there is
nothing to route), and for a hub the OS routing table across per-peer devices. What is
given up: the router's single-node fan-out and its `ingress`/`sd` integration.

**2. Does `OpenTunnel` need a `network`?** Yes. A tun handler writes one IP packet per
`Write` and expects one packet per `Read`; a TCP endpoint coalesces and splits, which
corrupts packet boundaries (the same reason `packetConn` and p2p's own `writeFrame`
exist). `OpenTunnelRequest` gains `network`; the host binds a TCP or a UDP socket
accordingly, and for UDP each datagram travels as one length-prefixed frame over the
smux stream. The reply's `endpoint` stays scheme-less — the caller knows which network
it asked for. TCP is the default, so existing deployments are untouched.

## Topology

Chosen: **symmetric — both ends are tun clients** (no hub, no tun server).

```
host A                                                host B
 gost  tun listener (10.10.0.1/30)                     gost  tun listener (10.10.0.2/30)
       tun handler (client, chain → node addr = B key)       tun handler (client, chain → A key)
         │ dialer: udp, connector: forward                     │   (mirror)
         ▼                                                      ▼
 p2p   udp endpoint E_A ◄─ channel(A→B) ─► E_B               p2p   (same, mirrored)
        + smux stream: smaller key opens, larger accepts
```

Both sides run the *same* gost config (only the peer key and device address differ).
The p2p stream is a virtual cable between two tun clients, and each side's local UDP
datagram endpoint is what the tun handler dials.

**Star (hub + N spokes)**: the hub runs N tun services, one device per peer (one /30
each), and the kernel routes between them (`net.ipv4.ip_forward=1`, the documented
multi-interface VPN setup). p2p provides one channel per peer. Full mesh on a *single*
device (N peers per tun handler) is out of scope — that would be a tun-handler redesign,
not a p2p one.

## Final config shape (side A; side B mirrored)

```yaml
p2ps:
- name: p2p-1
  plugin:
    type: grpc
    addr: 127.0.0.1:8003
    # token: gost            # set when the p2p host runs with --token

services:
- name: tun-0
  addr: :0                   # never bound in client mode, but must not be empty
  handler:
    type: tun
    chain: chain-0           # chain without forwarder → client mode (new rule)
  listener:
    type: tun
    metadata:
      net: 10.10.0.1/30
      mtu: 1420
      # route: 192.168.123.0/24   # to reach networks behind the peer (hub/star)

chains:
- name: chain-0
  hops:
  - name: hop-0
    nodes:
    - name: node-0
      addr: <B public key>   # in p2p mode addr IS the peer key (base64 rawurl)
      dialer:
        type: udp            # datagram semantics: chooses the UDP tunnel endpoint
      connector:
        type: forward        # transparent; must be explicit, the default is http
      metadata:
        p2p: p2p-1

log:
  level: debug
```

```bash
# side A p2p host (no --target, no --link)
p2p --derp wss://derp.example.com/derp --key a.key \
    --addr 127.0.0.1:8003 --stun derp.example.com:3478
```

The CLI form now reads equally well:

```bash
gost -C p2ps.yaml \
  -L "tun://:0?net=10.10.0.1/30&mtu=1420" \
  -F "forward+udp://<B key>?node.p2p=p2p-1"
```

`-F` attaches the chain to the service (which triggers client mode); unprefixed query
parameters land in handler, listener and service metadata alike
(`x/config/cmd/cmd.go:592`), and `node.`-prefixed ones in node metadata
(`x/config/cmd/cmd.go:642`). `p2ps:` only exists in the config file, so `-C` is still
required.

### Why not `direct`/`virtual` nodes

`dialer: virtual`/`direct` (`x/dialer/direct/dialer.go:37`) returns `&conn{}` without
ever touching `options.Dialer` — and the p2p wrapper takes over dialing precisely by
replacing `options.Dialer`, so the tunnel would never be opened. `connector:
virtual`/`direct` (`x/connector/direct/connector.go:51`) is the same type and *ignores
the dialed conn*, dialing the destination itself with the internal net dialer — it would
bypass the tunnel and try to dial the public key as an address. The documented
transparent connector is `forward` ("does no logic of its own, used with a data
forwarding channel", `docs/en/docs/reference/connectors/forward.md`, whose example —
`dialer: tls` + `connector: forward` — has exactly this shape); `tcp` is code-equivalent
but reads like a protocol.

### Client/server decision (the handler change)

Today `h.hop` is set only by the service-level `forwarder:`
(`x/config/parsing/service/parse.go:430` is the only caller of `Forward()` in the tree),
and `x/handler/tun/handler.go:92` sends `h.hop == nil` straight to `handleServer` — a
server that binds a UDP socket and waits for peer heartbeats. The handler cannot reach
the chain's nodes either (`Chainer` only has `Route()`, nothing to enumerate nodes), so
without a forwarder there is no way into client mode.

The change (the same idiom `serial`/`unix` handlers already use — see
`x/handler/serial/handler.go:229` and `x/handler/unix/handler.go:217`):

- `forwarder` present → the hop node it selects (unchanged);
- no `forwarder` but `h.options.Router.Options().Chain != nil` → **client mode**, with an
  empty dial address;
- neither → server mode (unchanged). `h.options.Router` and `Options()` both need nil
  guards.

An empty dial address is safe: the link is transparent to tun, the `forward` connector
never reads the address, and `Chain.Route` / `Resolve` / `Route.Dial` all tolerate an
empty string (`x/chain/chain.go:132` does not parse the address). The p2p **peer comes
from the chain node's addr** (`Transport.Dial(ctx, node.Addr)`), not from this address.
The one consequence: a non-transparent connector (http/socks5/ss/…) has no destination,
so those still need an explicit `forwarder`.

**Compatibility note (goes into the release notes and the tun docs):** `tun server +
chain` used to be dead config — the chain was built and never read (`h.options.Router` is
read only at `x/handler/tun/client.go:41`; the server branch and the tun listener never
touch the chain). It is now interpreted as client mode. The shape does occur in practice
because `-F` attaches the chain to every `-L` service in CLI mode
(`x/config/cmd/cmd.go:210`). Treating that combination as invalid was a deliberate call;
the docs must say so.

**The forwarder still earns its place** for direct (no-chain) dialing — the documented
client example `tun://:0/SERVER_IP:8421`, where it is the real peer address — and for
non-transparent connectors. It also decides whether the handler's `network` is `udp`
(address has a port → heartbeats) or `ip` (no port → none).

## Changes

### plugin/ — protocol

- `plugin/p2p/proto/p2p.proto`: add `string network = 2;` to `OpenTunnelRequest` (values
  `tcp`/`udp`, empty = `tcp`). Regenerate from the module root as `plugin/CLAUDE.md`
  requires (`protoc --proto_path=. --go_out=. --go_opt=paths=source_relative
  --go-grpc_out=... p2p/proto/p2p.proto`) so the registered file name stays
  `p2p/proto/p2p.proto`.

### x/ — GOST side

- `x/handler/tun/handler.go`: the client/server decision above, extracted into a small
  `selectTarget(ctx)`; one branch left in `Handle`. Nil guards on `h.options.Router` and
  `Options()`. The client-mode `dst` log field degrades to empty without a forwarder —
  keep the existing format.
- `x/p2p/tunnel_dialer.go`:
  - `TunnelProvider.OpenTunnel(ctx, network, peer)` — thread the network the inner dialer
    asked for.
  - `tunnelBaseDialer.Dial` currently hardcodes `"tcp"`: normalize the incoming network
    (`udp`/`udp4`/`udp6` → `udp`, everything else → `tcp`), pass it to `OpenTunnel` and
    use it for the endpoint dial.
  - `SupportedDialer`: allow `"udp"` (its comment says the wrapper's contract is "inner
    dials one plain TCP stream" — it must become "a stream, or a datagram conn for udp").
- `x/p2p/plugin/grpc.go`: set `Network` on the request (`grpc_test.go` too).
- `x/dialer/udp/dialer.go`: `c.(*net.UDPConn)` is a hard assertion, so any wrapped base
  dialer panics — and the p2p wrapper returns a `tunnelConn`. Keep the existing branch
  when the assertion holds (downstream code uses `*net.UDPConn` to mean "direct"), add a
  `net.Conn`-based fallback with the same `ReadFrom`/`WriteTo` semantics otherwise.
- `play/p2p-tun.yaml`: the new example (both sides + the p2p host commands), i.e. the
  config above. Note that **`connector: {type: forward}` must be explicit** — the node
  parse default is `http`, which would speak CONNECT over the link; and that
  `direct`/`virtual` mean "no hop, dial the destination directly", the opposite of what is
  wanted here.
- Optional, **not required by this design**: making the tun handler start keepalives when
  `keepAlive`/`ttl` metadata is set instead of only when the forwarder address carries a
  port (`x/handler/tun/client.go:51`). With two tun clients there is no server learning
  addresses, so heartbeats only add noise plus a 30 s read deadline that forces pointless
  re-dials; the example therefore omits `keepAlive`. Can be added on request.
- Docs (separate repo, follow-up): `docs/*/tutorials/tuntap.md` and the p2p blog post,
  both gaining the new "chain means client" rule and the compatibility note.

### p2p/ — the datagram tunnel replaces the device link

New `p2p/udp.go`:

- **Datagram endpoint** — `net.ListenPacket("udp", bind:0)`, tracking the last-seen client
  address (gost dials a connected socket, so the source is stable; a re-dial changes it
  and last-writer-wins). Datagram in → `writeFrame(current stream)`, dropped when the
  stream is down (IP tolerates loss). One reader goroutine per stream: `readFrame` →
  `WriteTo(client)`.
- **Per-peer channel** — `{endpoint, current stream, opener, refs}`. Role by public-key
  ordering, the same rule as the smux session and the old `link.go`: the smaller key
  opens. The opener runs `channelLoop` (the shape of the old `linkLoop`: `OpenStream` →
  serve → backoff retry, `<-e.stop` to exit); the responder opens nothing and waits.
- **Stream tagging** — a stream carrying a datagram channel is prefixed with a 4-byte
  magic (`P2PU`) before the first frame, so the responder can tell it apart from an
  ordinary tunnel stream and still bridge untagged ones to `--target` as today (peek 4
  bytes, re-prepend on mismatch). Length alone is not enough: a normal tunnel stream's
  payload is arbitrary bytes.
- **Reuse** `writeFrame`/`readFrame`/`writeAll`/`maxFrame`, moved out of `dev.go` into
  `p2p/frame.go` (the same 2-byte BE prefix format as `router`'s `packetConn`).

`p2p/server.go`:

- `OpenTunnel`: validate `network` (`tcp`/`udp`, else `InvalidArgument`); for `udp`
  require engine mode, get or create the peer channel and reply with its endpoint.
  `CloseTunnel` decrements the channel's refcount and tears it down at zero (closes the
  endpoint socket and the stream; the next `OpenTunnel` rebuilds it).
- Stub mode (no `--derp`): `udp` tunnels pump datagrams straight to the peer `host:port`
  — a dev aid mirroring the existing stub TCP bridge, and the hook for a cheap e2e test.

`p2p/engine.go` + `p2p/direct.go`: add the `channels` map and accessor. In `acceptLoop`
(`direct.go:639`, which already branches on `e.dev` for device mode), peek the 4-byte tag
on every inbound stream: tagged → serve on the peer's channel, and if the channel does
not exist yet (the peer's gost has not dialled) close it at debug level and let the
opener's backoff retry — a normal startup race, not an error. Untagged → re-prepend and
bridge to `--target` exactly as today.

Delete `dev.go`, `dev_linux.go`, `dev_other.go`, `dev_test.go`, `link.go`, and the
`--link` flag, the `links:` config and its validation in `p2p/main.go` / `p2p/config.go`.
p2p stops opening devices entirely. (tap users keep GOST's `tap` handler.)

Docs: `p2p/CLAUDE.md` (flag table, positioning, trust boundary — the endpoint is
loopback-only like the gRPC control plane, the data plane is still unencrypted),
`p2p/README.md` and `README.zh-CN.md`.

## Implementation notes (2026-09-11)

The design review flagged seven unpinned details before coding; each is resolved as follows.

1. **Tag peek blocked the accept loop.** Classification moved out of `acceptLoop` into a
   per-stream goroutine (`serveInbound`), and the peek is bounded (`channelTagTimeout`, a
   var so tests can shorten it) with a `prefixConn` replaying whatever a partial read
   consumed. Bounding is not optional: an *untagged* stream may legitimately be silent (a
   bridged protocol whose target speaks first) and would otherwise deadlock that bridge.
   Covered by `TestPeekTag` and `TestEngineIdleStreamBridged` (greeter-first target).
2. **`channelLoop` outlived its channel.** The loop now selects on `ch.stop` (channel-scoped,
   closed by teardown) instead of the engine's, and re-checks `ch.stopped()` after
   `OpenStream` returns so a stream opened during teardown is closed rather than published
   to a dead channel. `TestChannelRefcount` asserts a rebuilt channel gets a fresh stop.
3. **Tag vs. frame ordering.** The opener writes the tag *before* the stream is published
   (`serveStream`/`setStream`), so the endpoint reader cannot frame ahead of it.
4. **Frames before the local gost dialled.** Dropped instead of written to an unknown
   address (`TestChannelDropsWithoutClient`).
5. **Stub-mode udp.** Removed rather than built: `udp` requires engine mode
   (`codes.InvalidArgument` otherwise), and the in-process relay harness covers the test
   need, so the stub pump would have been dead spec.
6. **`addr: :0` comment.** Corrected — `net.ResolveUDPAddr("udp", "")` yields `:0` without
   error, the listener does no further validation.
7. **Chain-means-client switch.** Now logged (`tun: chain without forwarder, running in
   client mode`) instead of being silent.

One gap the design missed and the tests caught: the endpoint learned its client address only
from a datagram it received, so a link whose peer speaks first would never come up (both
sides waiting). GOST now announces itself with an empty datagram right after dialling a udp
endpoint (`tunnelBaseDialer.Dial`), and `readLocal` records the address for zero-length
datagrams too.

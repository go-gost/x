# hopGroup: Conditional Hop Group Selection for Forwarder

## Problem

### Conflict: probe `Reset()` vs `failCodes` `Mark()`

`chain.Node` has a single `selector.Marker` ([core/chain/node.go](core/chain/node.go#L218)). Two mechanisms share it:

| Mechanism | Calls | Lives in |
|-----------|-------|----------|
| `failCodes` | `node.Marker().Mark()` on matching HTTP status | HTTP response path (`sniffer_http.go:577`) |
| Probe | `node.Marker().Reset()` on successful health check | Per-node probe goroutine |

The conflict:

```
1. HTTP response 429 → failCodes → node.Marker().Mark()  // count=1, node excluded
2. Probe goroutine → TCP health check succeeds → node.Marker().Reset()  // count=0, node back!
3. Next request hits same node → 429 again
```

`Reset()` has no way to know whether the mark came from failCodes or a genuine network outage. It clears both. The probe restores a node that failCodes intentionally excluded — rendering failCodes ineffective.

### Current workaround: probe-based pseudo-grouping

Users work around this by putting nodes with different probe configs into one hop, using probe to create implicit groups. This makes the hop configuration bloated and the grouping intent invisible.

### Chain level has `chainGroup`, hop level has nothing

`x/chain/chain.go` already has `chainGroup` — groups multiple `chain.Chainer` with a selector, used at the router level. The forwarder (`handler.Forwarder`) can only accept a single `hop.Hop`. No equivalent grouping exists at the hop level.

## Solution

**`hopGroup` separates the two markers into different levels:**

| Level | Marker owner | Controlled by | Semantics |
|-------|-------------|---------------|-----------|
| **hopGroup entry** | `hopEntry.marker` | Probe (network health) | Is the hop reachable at all? |
| **Node (within hop)** | `node.Marker()` | failCodes (HTTP response status) | Should this node get this type of traffic? |

Probe runs at the hop entry level and marks the entry — not individual nodes. A marked hop entry is excluded from the group selector's pipeline (FailFilter). failCodes continues to work at the node level within each hop — no Reset() interference.

**Secondary benefit:** explicit grouping replaces the implicit probe-based pseudo-grouping. Each named hop in the group has its own selector, nodes, and reload source — independently manageable via API.

## Design

**`hopGroup` implements `hop.Hop`** — zero handler changes, drop-in compatible with the existing `Forwarder.Forward(hop.Hop)`.

### Per-hop config

| Field | Purpose |
|-------|---------|
| `hop` | Named hop reference from registry |
| `matcher` | `routing.Matcher` DSL — conditional routing. `Bypass(...)`, `Host(...)`, `PathPrefix(...)`, etc. Nil = unconditional (catch-all) |
| `probe` | `ProbeConfig` — hop-level health check for dynamic failover |

### hopEntry struct: hop + markable wrapper

```go
type hopEntry struct {
    hop     hop.Hop
    matcher routing.Matcher   // nil = unconditional
    probe   *probeConfig       // internal parsed probe config
    marker  selector.Marker   // for selector.FailFilter exclusion (hop-level, NOT node-level)
}
```

`hopEntry` implements **both** `hop.Hop` (via `Select()` delegation) and `selector.Markable` (via `Marker()`) so it can be passed to `selector.Selector[hop.Hop]` — the selector's `FailFilter` checks `selector.Markable` dynamically. Same mechanism as node-level fail marking in `chainHop`, but at a different level.

### Select() logic

```
1. Matcher filter:
   for each entry in group:
     if entry.matcher == nil → eligible
     else → build routing.Request from SelectOptions, entry.matcher.Match(request)

2. Selector:
   cast eligible entries to []hop.Hop (type-erased slice, one allocation per Select)
   apply FailFilter (exclude marked entries via selector.Markable) then strategy
   → pick one hopEntry (type-assert back from hop.Hop)

3. Delegate:
   return entry.hop.Select(ctx, opts...)
```

The `[]*hopEntry` → `[]hop.Hop` conversion allocates a new slice per call. Acceptable — hop selection is per-connection, not per-packet. An alternative (store entries as `[]hop.Hop`, type-assert in the probe goroutine) would push the allocation to the non-hot-path, but makes matcher access uglier. Either way works; pick the cleaner one.

Nil matcher + nil probe = always eligible (catch-all). Hops with matchers that don't match simply never get selected (correct — traffic ruled out by condition).

### Probe: hop-level health check

Runs at the **hop group entry** level, not at the node level. Periodically samples a node from the hop and marks the **hop entry** (not the node) on failure.

- Probe goroutine runs on `hopGroup` lifetime (started on creation, stopped on Close)
- Each probe tick: `hop.Select()` → get a node → TCP/HTTP/ICMP probe to node.Addr
- Default probe interval: 30s (same as node-level default from `parseProbeConfig`)
- On failure: **`entry.marker.Mark()`** (marks the hop entry, not the node)
- On success: **`entry.marker.Reset()`** (clears the hop entry mark, not the node)
- If a hop has no probe config: entry is never marked (always eligible)

**Key design property:** probe writes to `entry.marker`, failCodes writes to `node.Marker()`. They never touch the same marker. Probe Reset() only clears the hop entry mark — it cannot undo a failCodes mark on a node.

**Sampling caveat:** `hop.Select()` picks one node per tick (round-robin/random). A single bad node in an otherwise-healthy hop could mark the entry if `maxFails=1` and the probe hits that node repeatedly. Mitigation: set `maxFails > 1` on the hop entry metadata, or ensure hop-level probes use `maxFails=N` where N ≥ the number of nodes in the hop.

This integrates with the selector's FailFilter — a marked hop entry is excluded from selection until a probe succeeds.

### Selector

Reuses `selector.Selector[hop.Hop]` with full pipeline: FailFilter → BackupFilter → strategy. Since `hopEntry` implements `Markable`, the selector can exclude unhealthy hop entries.

## Files

### NEW: `x/hop/group.go`

- `hopEntry` struct — implements `hop.Hop` (via `Select()` delegation) and `selector.Markable` (via `Marker()`)
- `hopGroup` struct: `{entries []*hopEntry, selector selector.Selector[hop.Hop], logger logger.Logger, cancelFunc context.CancelFunc}`
- `HopGroupOption` functional options type — mirrors the existing options pattern in `x/hop/hop.go`:
  ```go
  type HopGroupOption func(*hopGroupOptions)

  type hopGroupOptions struct {
      entries  []*hopEntry
      selector selector.Selector[hop.Hop]
      logger   logger.Logger
  }
  ```
- `NewHopGroup(opts ...HopGroupOption) *hopGroup`
- `Select(ctx, opts...) *chain.Node` — matcher filter → selector pipeline → delegate
- `Nodes() []*chain.Node` — aggregate all nodes across all entries for introspection/API. Implements `hop.NodeList`. Returns a snapshot — hot-reload entries may change the underlying set between calls (consistent with `chainHop.Nodes()`).
- `Close() error` — stop probe goroutines
- Probe goroutine: reuses `x/hop/hop.go` probe infrastructure (same as node probes)

### MODIFY: `x/config/config.go`

```go
type ForwarderConfig struct {
    // ... existing fields unchanged ...
    HopGroup *ForwardHopGroupConfig `yaml:"hopGroup,omitempty" json:"hopGroup,omitempty"`
}

type ForwardHopGroupConfig struct {
    Hops     []*ForwardHopConfig `yaml:",omitempty" json:"hops,omitempty"`
    Selector *SelectorConfig      `yaml:",omitempty" json:"selector,omitempty"`
}

type ForwardHopConfig struct {
    Hop     string             `yaml:",omitempty" json:"hop,omitempty"`
    Matcher *NodeMatcherConfig `yaml:",omitempty" json:"matcher,omitempty"`
    Probe   *ProbeConfig       `yaml:",omitempty" json:"probe,omitempty"`
}
```

### MODIFY: `x/config/parsing/service/parse.go`

Extend `parseForwarder()` with precedence:

```
HopGroup > Hop > Name > Nodes
```

- If `cfg.HopGroup != nil`: build `hopGroup` from listed hops. `cfg.Hop`, `cfg.Name`, and `cfg.Nodes` are ignored.
- Else if `cfg.Hop != ""` or `cfg.Name != ""`: look up named hop from `registry.HopRegistry()` (existing behavior).
- Else fall back to inline `cfg.Nodes` (existing behavior).

When building from `HopGroup`:
- Resolve `ForwardHopConfig.Hop` from `registry.HopRegistry()`
- Parse `Matcher` via existing matcher parsing (same as node parsing)
- Parse `Probe` via existing probe parsing (same as node probe parsing). Default probe interval: 30s (matches node-level default from `parseProbeConfig`).
- Reuse existing selector parsing for group selector
- `Name` set on `ForwarderConfig` is ignored when `HopGroup` wins (no shadow hop ref)

### NO CHANGES

- `core/hop/hop.go` — hopGroup implements existing `Hop` interface
- `core/handler/handler.go` — `Forwarder.Forward(hop.Hop)` unchanged
- `x/handler/forward/local/` and `remote/` — call `h.getHop().Select()`, no knowledge of group
- `x/registry/` — hopGroup is constructed at config parse time
- Probe infrastructure — reuse existing `x/hop/hop.go` probe patterns (TCP/HTTP/ICMP dial checks)

## Config Example

```yaml
hops:
  - name: h-web
    nodes:
      - addr: 10.0.1.1:8080
      - addr: 10.0.1.2:8080
  - name: h-api
    nodes:
      - addr: 10.0.2.1:8080
        failCodes: [429, 502, 503]    # node-level: HTTP status failover
      - addr: 10.0.2.2:8080
        failCodes: [429, 502, 503]
  - name: h-internal
    nodes:
      - addr: 192.168.1.1:3128

services:
  - name: multi-hop
    addr: :8000
    handler:
      type: tcp
    forwarder:
      hopGroup:
        hops:
          - hop: h-api
            matcher: PathPrefix("/api/") && Host("*.example.com")
            probe:
              type: http                  # hop-level: network health (won't touch node markers)
          - hop: h-internal
            matcher: Bypass("10.0.0.0/8", "*.internal")
          - hop: h-web                     # no matcher, no probe = catch-all
        selector: rr
```

| Traffic | Match | Result |
|---------|-------|--------|
| `GET /api/users` on `app.example.com` | matcher hit | `h-api` (if probe healthy) |
| `GET /` on `www.example.com` | no matcher hit → catch-all | `h-web` |
| Raw TCP to `10.0.5.3:5432` | Bypass match | `h-internal` |
| All `h-api` nodes return 429 → failCodes marks nodes → excluded by FailFilter | → fallback to catch-all | `h-web` |
| `h-api` server network-down → probe fails → hop entry marked | → FailFilter excludes | fallback to catch-all |
